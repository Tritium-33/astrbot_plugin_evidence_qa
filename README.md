# 证据问答与会话路由

[更新日志](CHANGELOG.md)

适用于 AstrBot 4.29.3 的私聊、群聊与 WebChat。闲聊沿用当前模型与人设，图片可交给视觉模型；资料问题交给研究模型，按内容选择联网或原生知识库。运行数据保存到 AstrBot 的插件数据目录，源码中不放测试、审计或构建文件。

## v0.4.0 的流程

```text
已触发的用户消息 → 一次任务规划（有图时同时理解画面）
  ├─ 日常聊天 → 当前模型 → 直接回复
  ├─ 联网查询 → 原生搜索 / 阅读 → 研究模型直接回答
  ├─ 本地查询 → 匹配的原生知识库 → 研究模型
  │             ├─ 技术参数、型号差异、结构原理 → 一次聚焦核验 → 答案
  │             └─ 普通文献概述 → 直接回答
  ├─ 资料目录 → 已缓存的目录与概览
  ├─ 追问来源 → 同会话已保存的证据 → 原文与出处
  └─ 生成图片、其他工具操作 → 交还原生 Agent
```

只有本地技术查询保留后置模型核验。回答模型内部生成逐项结论和逐字引文，核验模型一次检查型号、改型后缀、阶段、条件、数量、单位与文段归属，并在同一次调用中修正错误条目。不会再整篇重写或二次审查。核验输入聚焦引用片段及已取得的邻接上下文，允许连续段落使用代称，不要求每段重复型号。历史回答和用户纠正不作为独立文献证据。

闲聊、联网和本地概述正常只需“规划 + 回答”两次模型调用；本地技术正常为“规划 + 回答 + 一次核验”三次。资料目录和来源追问只需规划，随后直接读取缓存。混合查询只核验含本地技术依据的条目，纯网页条目直接保留。

初次检索并行执行，最多四次。回答模型需要更多材料时，可通过本轮原生函数工具 `evidence_lookup` 换词搜索或读取网址，最多两次，检索总计最多六次。这发生在最终回答之前，不是回答后的审查或重写；每轮工具交互会增加模型调用和耗时。明确只查本地时，工具仍限于本地。材料足够就直接结束。

联网和普通概述直接生成自然语言，不要求 JSON 或逐字引文，不做后置审查。内部来源标记在发送前移除。直接输出的事实质量取决于回答模型；本地技术核验也依赖模型判断。本地核验未通过的条目不会发送，已通过的条目及混合查询中的网页条目保留。无结果或流程失败沿用静默策略，原因写日志/trace，不发送失败模板或无关原文。

各线路保留同一会话的历史和人设；GCP 提供的群历史同样沿用。通常按 AstrBot conversation ID 保存来源；GCP 尚未创建原生会话时按对应平台会话保存，不与其他群或私聊混用。只从持久历史中移除本插件的临时检索材料及工具过程，保留最终回复；下轮可继续承接话题。LivingMemory 的隔离另见下文。

## 模型与搜索配置

1. 在 AstrBot 配置默认聊天模型，例如 Gemini；保留你需要的原生回退模型。插件不改全局模型或原生额度回退配置。
2. 插件配置 `worker_provider_id` 填 **Provider ID**（例如你的 DeepSeek 提供商 ID），负责规划、本地技术单次核验与手动目录概括。
3. `research_provider_id` 填资料回答模型的 Provider ID，通常也选 DeepSeek。留空沿用当前模型。用户本轮显式选模型时优先保留其选择。
4. 在 AstrBot 打开原生 `web_search`，选择搜索服务并配置搜索密钥。聊天模型的 Key 不等于搜索服务已启用。
5. 保留 AstrBot 原生知识库选择、Embedding 和 Rerank 配置。插件调用原生 `kb_manager.retrieve`，没有另建向量库或另做重排序。

### 图片、表情包与群聊

`vision_provider_id` 填实际支持图片输入的 Provider ID，例如你已验证可看图的 Gemini。普通看图聊天由它回复；需要查资料时，它先识别画面和任务，再由 `research_provider_id` 回答。纯文本规划及本地技术核验仍使用 `worker_provider_id`。留空先使用原生图片描述提供商，再使用当前模型；给纯文本 API 勾选图片能力不会让该 API 获得视觉能力。

纯图片、图文混合、引用中的图片、带 URL 的 NapCat `mface` 表情均可进入流程。GIF 等动画沿用原生抽帧拼图；模型据画面、文字和聊天上下文理解梗图，不默认长篇描述。仅有 QQ 内置表情编号、没有图像的消息不冒充看到了画面。图片规划失败时仍交回看图聊天流程；没有生成规划的附件请求继续走原生处理，不再直接截成空回复。

视觉规划和简洁画面说明合并在一次模型请求中，不额外运行独立的描述模型。切换到纯文本回答模型时附上这份说明，避免继续传图片触发第二次原生描述或被原生图片回退覆盖选模。用户显式选模型仍优先；画面说明并非经核验的外部技术证据。

`enable_group` 默认开启，只接管已经触发的群回复，不主动决定何时插话。与 Group Chat Plus 的上下文恢复钩子衔接，保留发言者、群历史、人设及附件。具体配置、频率建议和测试步骤见 **[Group Chat Plus 与看图配置](GROUP_CHAT_PLUS.md)**。

联网默认使用 AstrBot 当前配置的搜索工具，支持 DeepSeek、Tavily、Bocha、Brave、Firecrawl、Baidu AI Search、Exa、AnySearch、SerpAPI。DeepSeek 和 Tavily 每次最多取 8 条搜索结果。页面按可读性及不同站点安排读取顺序，同一路径的跟踪参数和语言参数变体合并，实际文章 ID 参数保留。

DeepSeek、Tavily、Firecrawl、Exa 每次搜索尝试读取至多 4 个不同页面，目标取得 2 个正文，读取失败会递补其他结果；保留搜索摘要供回答。也可按模型的后续请求直接读取具体 URL。其他服务保留搜索摘要并明确其性质，不假称已经读过网页全文。网页失败记录脱敏后的异常详情，不把无关本地资料当作替代品。

“最新动态”“越野越好”等请求分别保留时效和广泛搜罗的意图；正式发布、媒体报道与社区传闻在回答中区分。模型按结果决定是否补查，不要求用户手动给搜索指令。这里使用 AstrBot 的原生搜索和阅读工具，不包含 Codex 的搜索服务，也不保证不同搜索供应商能返回相同结果。

新闻、近期动态等通常联网；主题匹配本地目录时才查本地。明确“只查本地/不要联网”时尊重要求，即使尚无目录缓存也可查询当前已选库。目录描述是范围提示，不是型号白名单。

## 资料目录：手动刷新

管理员在机器人私聊中发送：

```text
/资料目录更新
```

初次使用及上传、删除、更换文档后执行一次即可。不需要自己总结书籍或添加条目。

- 启动只加载 `catalogue.json`，不扫描正文、不调用模型，没有定时刷新任务。
- 手动更新时只读扫描原生文档，计算内容指纹，使用标题和分布抽样自动概括范围。仅新增/变化的文档调用概括模型；删除文档会从缓存移除。
- 目录不是全文索引。改型/参数的确证仍来自实际检索，摘要不能证明某主题在书中不存在。
- 失败保留上次完整缓存。刷新不会重新嵌入或改变原始知识库。
- 提问时从内存读取已选库的概览，放进原有规划请求；没有额外的“读取目录”模型调用。增加的输入量随文档概览数增长。

目录刷新命令需要 AstrBot 管理员权限。配置管理员后使用；命令结束会报告文档数和重新概括数。

## 回复长度与来源

日常回复在生成前提示通常 1–3 句、约 15–60 字、尽量不超过 80 字，强调完整自然句子。首次回复直接发送，不另调模型压缩，也不截断字符串；字数是表达指导，不是程序硬上限。明确要求长文、小说或详细说明的任务豁免。

资料回答默认只给结论；原文、文档位置或网页 URL 保存在内部证据快照。来源追问显示对应文献引文或网页链接。本地技术回答保留逐字引文；直接回答保存模型标注的段落与来源关联，不等于额外核验过支持关系。若模型未标注来源，则明确列出“本轮检索到的来源（未建立逐句对应）”，不会伪造逐句引文。随后可以问：

- “刚才这个结论的原文和出处是什么？”
- “前面 906B 携弹量那条的来源呢？”
- “只给第二项的出处。”

来源取自对应回答当时的证据，不重新搜索拼出新出处；按平台会话及 AstrBot conversation ID 隔离。换新会话不继承旧会话证据。目前保留最近 20 条资料记录，规划展示本会话所保留记录的问题，最近 4 条额外提供逐项结论供定位。无对应证据时不冒用其他轮次的来源。

若人设写了“每次必须列出出处/长篇分析”，建议去掉该固定输出格式，保留事实准确和自然聊天要求；插件也会附加本轮格式规则。

## 与型号兼容插件、LivingMemory 一起用

- 型号兼容插件仍处理本地检索的别名、改型约束和邻接片段。这里不修改型号词典或语料。
- Rerank 使用 AstrBot 原生设置；未配置 Rerank 不会凭空生成重排。
- LivingMemory **2.8.1 / 2.8.2** 的私聊入口可被本插件跳过。默认资料轮、来源轮不进入记忆召回/记录；日常轮正常。
- “这轮别记”与混合提问可以请求跳过本轮记录。只有实际观察到召回及记录入口均被跳过，日志才记 `memory_isolated=true`。
- 不删除已有长期记忆，不清空聊天历史，不承诺撤销之前已写入的错误记忆。

建议分开测试：先闲聊，再问本地型号参数，再问最近 Gemini 新闻，随后分别追问两条来源。清洁会话可排除旧错误回答干扰；测试时核对 trace 的 `plan.source`、`operations[].channel`、`sources`、`items` 和 `timings`，不要仅凭回复自称“查询了知识库”判断。

## 超时与运行记录

| 设置 | 默认值 | 范围 |
|---|---:|---|
| `model_timeout_seconds` | 90 秒 | 每次规划、本地技术核验或手动目录概括 |
| `retrieval_timeout_seconds` | 45 秒 | 每次本地检索或联网搜索及其正文读取 |
| `page_timeout_seconds` | 15 秒 | 单个网页读取 |
| `turn_timeout_seconds` | 240 秒 | 从规划开始到答案核验结束，不含排队/发送 |
| `save_traces` | 开启 | 最近 20 份资料轮诊断记录 |

原生回答及工具交互还受 AstrBot 提供商自身超时与本插件整轮预算约束。取消多次审查减少的是串行调用，实际速度仍取决于模型、搜索及网页读取，不能保证固定秒数。

文件位于 `data/plugin_data/astrbot_plugin_evidence_qa/`：

- `catalogue.json`：手动刷新的资料范围。
- `evidence.json`：来源追问所需的最近 20 条证据快照，即使关闭诊断 traces 也保留。
- `traces/`：开启时保存本轮来源、答案、路由、调用耗时与记忆隔离状态；`answer_mode` 区分 `direct` 与 `local_technical`。只有本地技术核验会产生 `validation`，记录草稿（最多 16000 字符，标记是否截断）、逐项问题及一次审查结果。网页读取错误含脱敏详情。包含私人提问与原文，请按私人数据管理。

## 兼容范围与验证边界

依赖 AstrBot 4.29.3 的 `_select_provider`、`collect_initial_request`、`_apply_kb` 和普通 `run_agent` 内部接口，加载日志报告接管四个入口。支持私聊、群聊与 WebChat，不接管 Live。Group Chat Plus 衔接按 V1.2.3.hotfix.2 的请求钩子验证；LivingMemory 2.8.1、2.8.2 隔离适配范围为私聊。群消息采集、Group Chat Plus 自行召回及独立记忆写入不在此隔离保证内，不能把“这轮别记”理解为所有群聊记忆路径均被阻断。升级后需要重新核验这些内部接口。

开发测试使用隔离的 AstrBot 原生代码、真实文献片段回放和明确的模型/搜索夹具。它能验证工具确实被调用、输出与历史一致、来源隔离及失败处理，不能证明任意模型总能正确分类、理解语义或读取网站。未安装到运行中的 AstrBot，也未以真实付费 API 做质量验收。
